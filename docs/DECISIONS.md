# 技术决策记录（DECISIONS.md）

> 规则：任何技术选型/架构决策必须记录在此（理由 + 否决项）。防止旧项目「UI 反复回滚、技术路线漂移」的教训重演。

## D-001 ｜ UI 框架：WPF (.NET 8)（2026-09-11）
- **决定**：新项目采用 **WPF + .NET 8**，C#。
- **理由**：
  - PRD 适用平台 Windows 10 1903+ / Windows 11 全系列，.NET 8 官方支持该范围（含 ARM64）；
  - 原生渲染：PDF 标注/手写、双页、竖排 RTL、动画、ClearType 等 PRD 功能在 XAML 可实现；
  - 内存指标（空闲 ≤50MB）可达成（Electron 基线 100MB+ 直接出局）；
  - 开发迭代快（对比 Rust/C++），与「发现 bug→当天修复→当天打包」工作流匹配；
  - PDF/压缩包生态成熟（PdfiumViewer/PDFsharp/SharpCompress），符合 PRD「复用成熟库」。
- **否决项**：
  - ❌ Electron / Tauri / 任何浏览器内核：历史教训（起点直连、网页端被用户否决；内存不达标）；
  - ❌ tkinter 延续：PRD 大量渲染功能（PDF 批注、双页、竖排、动画、模糊背景）tkinter 不可实现或极难；
  - ❌ Rust/egui：内存最优但迭代太慢，与快速交付冲突（保留为远期评估）。
- **备注**：本机（开发机）无 .NET SDK，需先安装 .NET 8 SDK 才能编译运行。

## D-002 ｜ 数据存储：本地 JSON + SQLite（2026-09-11）
- **决定**：`data/` 目录 JSON（配置/进度/标注等小数据）+ SQLite（规模化藏书索引）。
- **理由**：用户数据与程序分离、可迁移（PRD 数据可迁移）；SQLite 应对大规模藏书（PRD 数字藏书管理）。
- **否决项**：❌ 云端优先存储（PRD 无强制联网）；❌ 闭源数据库组件（硬约束）。

## D-003 ｜ 版本分级：M1(P0) → M2(P1) → M3(P2)（2026-09-11）
- **决定**：按 PRD 优先级分三里程碑交付，每里程碑出可运行版本。
- **理由**：PRD 功能量极大（40+ 格式、PDF 专业、云同步、应用锁、插件、20+ 语言），一次性实现不可控；分里程碑可尽早交付可用核心。
- **否决项**：❌ 先做 P2 增强功能（本末倒置）；❌ 无限期停留在 P0（用户要的是完整版）。

## D-004 ｜ 解析引擎：自研 + 成熟库结合（2026-09-11）
- **决定**：TXT/EPUB/UMD 等自研解析（逻辑简单、可控）；MOBI/AZW3 评估移植旧项目逻辑；PDF 用 PdfiumViewer；压缩包用 SharpCompress。
- **理由**：PRD「禁止重复造轮子，全部自包含可审计」；旧项目 parsers.py 已有 818 行可移植参考。
- **备注**：编码识别（40+ 编码）复用 UDE 方案或移植 chardet 逻辑。

## D-005 ｜ 内存指标现实：WPF 基线 vs PRD ≤50MB（2026-09-12）
- **实测**：Release self-contained 单 exe 便携版——工作集 138MB / 私有内存 91MB（空闲）；Debug 144MB。R2R 对工作集影响甚微。
- **结论**：PRD 6.1「空闲 ≤50MB」在 WPF + .NET 8 下**不可达**（WPF 框架加载基线即 80–120MB）；`ServerGC=false`+`TieredPGO` 已尽力而为。
- **权衡**：
  - ✅ 接受基线（推荐）：WPF 换来 PRD 大量渲染能力（PDF 批注/双页/竖排/动画/模糊），内存换取功能密度；旧项目 tkinter 虽 ~50MB 但无法实现 PRD 渲染项。
  - ❌ WinForms：内存 ~40–60MB 达标但视觉/动画/数据绑定能力不足（D-001 已否决）。
  - ❌ 自绘（SkiaSharp/Direct2D）：~30–50MB 但全自绘开发量数月级，违背快速交付。
- **执行**：M1–M3 均以「功能完整优先，内存尽力优化」为原则；PRD 6.1 目标标记为「参考值」，最终验收以用户实际体验（不卡顿、秒开）为准。

## D-006 ｜ 语言边界：主体 C# + 进程级混合（2026-09-12）
- **决定**：主体保持 C#/.NET；值得跨语言的模块（PDF 引擎、AI 爬虫/OCR 等）以**独立子进程/本地服务**方式引入（HTTP/JSON 或 stdio），不在进程内嵌多运行时。
- **理由**：多语言混用收益集中在重模块（PDF/OCR/AI），TXT/EPUB/MOBI 解析换语言收益≈0；内嵌 Python/Node 运行时会使内存与体积失控，违背 D-001 低内存硬约束。
- **否决项**：❌ 进程内多运行时（Python.NET 内嵌解释器等）；❌ 为「语言统一性」阻止未来子进程服务（不设限）。

## D-007 ｜ 功能融合：四大能力中心（2026-09-12）
- **决定**：产品功能按**用户意图**组织为四大能力中心——① 元数据智能中心（智能整理流水线：扫描→置信度→修正→补全→一次确认）；② 格式解析中心（统一 IBookParser，打开即读）；③ 内容体验中心（读/听/排版/标注融合在阅读上下文）；④ 系统服务中心（统一分类设置面板 + 托盘）。
- **理由**：旧项目按技术手段堆功能（爬取/补全/对比/AI 各自入口）导致臃肿；PRD 功能量极大，逐条铺开必重蹈覆辙。融合后：核心功能 3 步内可达、书架按钮 ≤8 个、数据只存一份。
- **硬约束**：新增功能必须先归位到某中心再排期；禁止新增散落按钮/顶层设置开关；入口命名用用户语言（"智能整理"）不用技术名词。
- **落地**：M1 格式解析中心已就绪；M2 第一步实现「智能整理」流水线（吸收旧项目全部爬取/补全/修正功能）；详见 PRD 附录 A。
